# Проверка рисков перед изменением

Шлюз «можно / нельзя продолжать». Правила общения и полномочий — в CLAUDE.md; здесь только порядок проверки.

## Когда обязательна
- перед публикацией страницы экосистемы (навык `sadykhan-publish`);
- перед загрузкой реальных данных куда угодно (навык `sadykhan-real-data-import`);
- перед подключением или вызовом корпоративной системы (навык `sadykhan-bitrix-orgsync` и любые 1С/ОФД/агрегаторы);
- перед изменением ролей, доступов, структуры базы страницы или удалением функций.

Мелкие правки текста и стилей без данных и доступов — достаточно пунктов 1 и 5.
Если проверка уже пройдена для этого же изменения в текущей задаче (например, внутри `sadykhan-agent-profile`), то при последующем `sadykhan-publish` повторяй только R2 и R10 — изменения после неё могли появиться только в коде.

## Порядок
1. **Опиши изменение одной строкой**: что меняется, какие файлы и данные затронуты, куда уходит результат (GitHub, закрытая страница, внешняя система).
2. **Пройди чек-лист** (каждый пункт: «ок» / «риск» / «не применимо»):

| Код | Проверка | Как проверить | Блокирует |
|---|---|---|---|
| R1 Персональные данные (Закон РК № 94-V) | Нет ФИО сотрудников, ИИН/БИН ИП, телефонов, e-mail, дат рождения вне необходимости. ФИО в наименовании контрагента-ИП допустимо как реквизит поставщика; каждое такое WARN просмотреть и подтвердить, что это контрагент, а не сотрудник | `python3 .claude/skills/sadykhan-risk-check/scripts/pii_scan.py <файлы или папка>` | да |
| R2 Реальные данные вне git | В коммит не попадают реальные цифры, договоры, выгрузки | `python3 .claude/skills/sadykhan-risk-check/scripts/pii_scan.py --git` (сканирует staged и последний diff) | да |
| R3 Секреты | Нет токенов, вебхуков, паролей в коде, чате и коммитах | тот же скрипт ищет `rest/<id>/<код>`, `token`, `password`, длинные ключи | да |
| R4 Права интеграции | Только чтение, минимальные scope (Bitrix24: `department`, `user_brief`) | прочитать настройки/переменные окружения; никаких методов записи | да |
| R5 Демо ≠ реальное | Имитация помечена «имитация/тестовые данные», реальное — «реальные данные, разовая загрузка» или «подключено»; ничего запланированного не показано как работающее | поиск в изменённом коде: новые статусы, плашки, тексты | да |
| R6 Потеря данных | Не перезаписываются данные пользователей в базе страницы (`kb`, `kbtext`, `kbconf`, `proc`, `procstate`), записи — с `if_version`; перед перезаписью — копия | `ArtifactData list` до изменения, сохранить в scratchpad | да |
| R7 Доступы и роли | Руководитель розницы видит только Retail; CEO и директор по контролю — всё; новые разделы фильтруют данные по `S.role` | прогон `sadykhan-publish` во всех ролях | да |
| R8 Ошибки ИИ | Выводы ИИ помечены как предварительные, есть источник и проверка человеком; числа — из данных, не из модели | просмотреть промпты и тексты новых функций | нет — фиксируй и сообщи |
| R9 Законодательство РК | Ссылки на НПА — со статусом «не верифицирован», правовые выводы — юристу | поиск ссылок на законы в изменении | нет — фиксируй |
| R10 Регрессия | Существующие функции не удалены; страница проходит автотест | `node .claude/skills/sadykhan-publish/scripts/check-page.js` | да |

3. **Устрани риски сам**, если это безопасно и в пределах задачи (обезличить, убрать секрет, добавить пометку «имитация», добавить фильтр роли), и повтори проверку пункта.
4. **Что нельзя устранить самому** (нужны права, решение руководства, юрист) — остановись и вынеси пользователю одним сообщением: риск, последствие, вариант решения.
5. **Итог** — короткая таблица в ответе: код, статус, что сделано. Продолжать можно только если нет открытых блокирующих рисков.

## Критерий результата
- все блокирующие пункты «ок» или «не применимо»;
- `pii_scan.py` завершился с кодом 0 для переносимых данных и для git;
- в ответе пользователю есть итоговая строка «Проверка рисков: пройдена» или перечень открытых рисков.
