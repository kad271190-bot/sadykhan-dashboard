# Схема профиля ИИ-аудитора (PROFILES)

Профили лежат в `demo/sadykhan-ai-ecosystem.html` в объекте `PROFILES` (`Object.assign(PROFILES, { ID: {...} })`). Формат записи:

```js
Object.assign(PROFILES, {
  RET: { ... },
  PRI: { ... },
});
```

Только одинарные кавычки, без шаблонных строк `` ` ``, без функций. Апострофы и кавычки внутри текста — «ёлочки». Язык — русский, деловой и конкретный. Никаких общих фраз вроде «контролирует процессы» или «анализирует документы»: везде указано, ЧТО именно, ПО КАКОМУ правилу/порогу и КАКОЙ результат.

## Поля

```js
ID: {
  edu: [   // 3–5 пунктов. Требования к компетенциям специалиста такого уровня — НЕ вымышленный диплом агента.
    'Уровень специалиста: высшее экономическое или финансовое образование (бакалавр/магистр) — как требование к компетенциям',
    'Квалификация на уровне международных сертификаций: CIA (внутренний аудит), ACCA DipIFR (МСФО), CFE (расследование мошенничества)',
    ...
  ],
  comp: [ ... ],      // 6–8 профессиональных компетенций, конкретных для направления (что умеет понимать и оценивать)
  methods: [ ... ],   // 4–6 методик аудита (выборка по МСА 530, сравнение с порогом, профиль против медианы, сквозная сверка документов, aging-анализ, бенфорд, трассировка серий и т.п.) — с пояснением, к чему применяется
  docs: [ ... ],      // 5–8 нормативных документов, стандартов и СОП. Законы РК — названиями из словаря LAW в demo/sadykhan-ai-ecosystem.html (без придуманных номеров статей). Внутренние — демо-СОП с кодами из RULES[*].norm (например «Демо-СОП СТ-03 «Кассовая дисциплина»»).
  tools: [ ... ],     // 3–5 инструментов анализа (например: «Правила-процедуры уровня 1 (код, детерминированно)», «Независимый пересчёт верификатором», «Автономный ИИ-анализ с журналом запросов к данным», «Поиск по базе знаний «Документы» с цитатой пункта»)
  daily: [            // 6–8 ежедневных контрольных процедур, по порядку выполнения
    { t: '06:00',
      what:  'Что конкретно проверяется (объект и выборка: «все чеки за прошедшую смену по каждому кассиру 103 аптек»)',
      rule:  'Правило и порог со ссылкой на норму («Демо-СОП СТ-03 п. 4.4: доля аннулирований > 2% чеков кассира — основание для проверки»)',
      data:  'Какие данные и документы анализирует («чеки и сторно 1С:Розница, данные ОФД, журнал ИТ-инцидентов»)',
      result:'Ожидаемый результат («кейс с расчётом доли и списком чеков → верификатор; при подтверждении — задача заведующему аптекой в Bitrix24, срок 3 дня»)',
      code:  'RET-02' },   // код процедуры из RULES, ТОЛЬКО если он есть в AGENTS[ID].rules; иначе null (= процедура запланирована, ещё не запрограммирована)
    ...
  ],
  kpi: [ ... ],       // 4–6 показателей, которые агент отслеживает ежедневно, с целевым значением/порогом («Доля аннулированных чеков по кассиру — порог 2%»)
  risks: [ ... ],     // 4–6 нарушений/рисков, которые выявляет или предупреждает (конкретные схемы)
  weekly: [ ... ],    // 3–5 еженедельных процедур (конкретно: что, по какой выборке, результат)
  monthly: [ ... ],   // 3–5 ежемесячных
  quarterly: [ ... ], // 3–5 квартальных
  sources: [          // 4–7 источников
    { s: '1C_RT', what: 'чеки, сторно, отложенные чеки, смены и логины касс', ds: 'receipts' },
    // s — код системы из списка ниже; ds — ключ тестового набора DATASETS из demo, если демо имитирует эти данные, иначе null
  ],
  outputs: [ ... ],   // 5–7 результатов работы с адресатом и сроком («Ежедневная сводка отклонений → заведующим аптек и директору розницы, 08:00»; «Задача в Bitrix24 ответственному по матрице ответственности»; «Аудиторское заключение по кейсу (факты, расчёт, норма, вывод, риск)»)
  checkedBy: [ ... ], // 2–4: кто проверяет выводы («Верификатор доказательств (VER) — независимый пересчёт показателей», «Ревьюер методологии (REV) — применимость нормы и логика», человек-эксперт из AGENTS[ID].expert)
  sendsTo: [ { to: 'MOZG', when: 'все подтверждённые отклонения для корреляции по объекту' }, { to: 'Служба безопасности', when: '…' } ], // 3–5; to — ID другого агента из AGENTS или роль человека
  triggers: [ ... ],  // 3–4 случая, когда агент инициирует дополнительный аудит (у какого агента/подразделения и почему)
  value: '1–2 предложения: практическая польза для компании (какие потери/риски предотвращает, в деньгах или времени — без выдуманных фактических цифр компании)'
}
```

## Коды систем для `sources[].s`

| Код | Система |
|---|---|
| 1C_RT | 1С:Розница (аптеки: чеки, остатки, перемещения, ревизии) |
| 1C_UT | 1С:Управление торговлей (опт: заказы, отгрузки, клиенты, лимиты, цены, склад) |
| 1C_BUH | 1С:Бухгалтерия (проводки, платежи, акты сверки, ЭСФ-реестр) |
| 1C_ZUP | 1С:ЗУП (кадры, табель, отпуска, увольнения) |
| OFD | Оператор фискальных данных |
| POS | Кассовая программа аптек |
| B24 | Bitrix24 (задачи, структура, согласования) |
| AGG | Агрегаторы и маркетплейсы: Kaspi, Glovo, Wolt, Яндекс, Aurma |
| BANK | Клиент-банк (выписки) |
| TEMP | Термологгеры складов, аптек и рейсов |
| MARK | Система маркировки и прослеживаемости ЛС |
| ESF | ИС ЭСФ (электронные счета-фактуры) |
| REV | Отзывы 2GIS / Google / Яндекс |
| DOCS | Раздел «Документы» — корпоративная база знаний (СОП, приказы, договоры) |
| REG | Внешние реестры: adilet.zan.kz, реестр лицензий, реестр отзывов серий, реестр юрлиц |
| PLAT | Данные платформы аудита: кейсы, вердикты, журнал, задачи |
| SD | IT Service Desk (инциденты) |

Ключи DATASETS (для `ds`): receipts, revisions, reviews, promos, clients, shipments, limitChanges, esf, aggOrders, sales1C, payments, purchases, offers, whInv, batchSales, temps, licenses, users1C, terminations, vacations, context, wplan, wsales, deliveries, prices, stockouts, intake, quarantine, lots, picking, transport.

## Важно

- Реальные интеграции ещё НЕ подключены (см. docs/ai-ecosystem/05-launch-log.md). Не пиши, что агент «уже получает данные из 1С» — пиши, что он берёт/проверяет (план работы), интерфейс сам покажет статус подключения.
- Агент — консультативный: только чтение бизнес-систем, запись — в кейсы, журнал и задачи; уважай поле `limits` агента.
- Учитывай реалии ГК Садыхан из demo: 103 аптеки (Тараз, Алматы, Алматинская обл., Астана), юрлица ТДФ/ДФ/СФЛ (розница), ТОО «Садыхан Премиум» (опт и склады), смена юрлица сети в 2026 (СОП прежнего юрлица), МОЗГ-оркестратор, трёхуровневая проверка (правило → верификатор → ИИ-аудитор + ревьюер), задачи в Bitrix24 по матрице MATRIX, сроки SLA по риску (критический 1 дн., высокий 3, средний 5, низкий 7).
- Проверка схемы после правки — одной командой (вывод должен закончиться списком ID без строк «нет …»):
  `node -e "const s=require('fs').readFileSync('demo/sadykhan-ai-ecosystem.html','utf8');const m=s.match(/const PROFILES = \{\};([\s\S]*?)const profOf/);global.PROFILES={};eval(m[1]);for(const[k,p]of Object.entries(PROFILES)){for(const f of['edu','comp','methods','docs','tools','daily','kpi','risks','weekly','monthly','quarterly','sources','outputs','checkedBy','sendsTo','triggers'])if(!Array.isArray(p[f])||!p[f].length)console.log(k,'нет',f);if(typeof p.value!=='string')console.log(k,'нет value')}console.log(Object.keys(PROFILES).join(','))"`

## Процедуры по реальным данным

Проверки, выполненные разово по реальной выгрузке, описываются не в `PROFILES`, а в `PROC_DAILY[ID]` (раздел «Аудит закупа»): поля `t, what, rule, data, result, real`, где `real` — ключ результата в функции `procCheck`. Они показываются с пометкой «Проверено по реальной выгрузке (разово)».
